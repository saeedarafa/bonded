# Contracts between agents

This file is the **single source of truth** for how the app, the database and the edge functions talk to each other. Every agent reads it before starting and after every merge.

**Status tags:**
- `live`: in `0001_mvp.sql` today.
- `planned (TASK)`: decided in [DESIGN_DELTA](plan/DESIGN_DELTA.md) and to be built by that task. Consumers build against the planned shape now.

**Changing a contract:**
1. The owner edits its section in the same PR as the code.
2. Add a change-log row.
3. A breaking change (rename, removal, changed error code) needs the consumer's ack in the PR, or the lead's decision.

Placeholders (D30):
- app scheme `bonded://`;
- bundle id `app.bonded.mobile`;
- invite domain `[your-domain]`.

**BE-14 recap semantics (D21):** `days_together` counts daily questions assigned in `[p_week_start, p_week_start + 7)` on or before today that have real answers from both current members. Streak-saver days and pack questions do not count. A solo couple returns zero days; no active couple raises `NOT_PAIRED`. Only revealed questions in the current pairing period contribute, including the existing pairing-day daily exception. Pre-pairing history, locked questions, ended/former couples and other couples cannot contribute. `is_full` checks active, unexpired entitlements of current members on the server at read time; exact expiry and former-member subscriptions do not unlock details. For free callers, `replies`, `reactions` and `most_loved_answer_id` are SQL null, including when there is activity. For premium callers, replies and reactions count current-member events created during those seven local dates, up to the server clock, on revealed pair-period questions (including activity on older questions). Reactions include answer and message reactions of every emoji (D45). Most-loved is an answer receiving at least one reaction during that window, ranked by reaction count, then answer creation time, then id (descending); message reactions do not choose an answer. No match returns null. No answer/message text is returned; fetch the selected answer through existing RLS. Retries only read state. Dates need not be Mondays; mobile supplies the displayed week's Monday. No caller clock/helper grants are exposed.

**D18 streak protection:** `get_streak.saver_available` is true only while yesterday can be repaired: current-member premium, a single missed day and no claim this local usage month. After protection, `last_completed_on` includes the protected day for continuity; `current`/`longest` preserve the previous run without adding a completed day (11 restores to 11). Today’s actual completion adds one. A later real offline completion of the protected day can count once under D17; the monthly claim stays spent. `completed_today` still requires today’s actual daily completion. Offline answers merge across protected days without double counting. Saver metadata is private/server-owned and cascades with the couple. Clients cannot choose a day, couple or timestamp.

**Screen 28 context (BE-11 / #121 P2):** `get_streak` and `use_streak_saver` append nullable `saver_reason` (`used_this_month` | `too_many_missed`) and `previous_streak`. `previous_streak` is the positive cached run that just expired (`last_completed_on` older than yesterday); it is null for a fresh/current/protected run, and is not a permanent history of earlier runs after a new completion replaces the cache. `too_many_missed` means an expired positive run cannot bridge yesterday under D18 (including consecutive missed days across month rollover); this takes precedence over quota. `used_this_month` means a repairable yesterday gap is blocked by this local month's claim, including after today is completed. Otherwise the reason is null (also when lack of premium alone prevents saving). Both fields use the couple's local date and current membership; no extra data is published or pushed.

**D39 expired preview details:** only `invite_preview` with a matching expired link token returns an object in `error.details`: `{inviter_name: string}`. Consumers should validate that shape and fall back to generic expired copy when absent/empty; do not log invite tokens or names. All other error shapes and `error.message` stay the same. The `invite-preview` avatar Edge endpoint still rejects expired tokens; token-link clients use the documented SQL fallback (§3) to obtain this error.

**D37 archive consent (BE-35, breaking; pending mobile ack/security review):** for a valid target invite, a solo caller must pass `p_archive_own: true` only from the archive-confirm sheet. Omitted, false or null raises `CONFIRM_ARCHIVE` before any request, archive, membership or failed-attempt write. Existing auth, paired, limiter and invite-validation errors retain precedence. Token joins archive immediately with consent; typed requests store consent privately for the exact current solo couple and keep it active until approval. Pending retries still require the flag and preserve the original request/expiry; an explicit retry can confirm a newly created solo space. `approve_join` may raise `CONFIRM_ARCHIVE` if the requester created/replaced a solo space since requesting, or a pre-migration request has no consent; the request stays pending, and the requester must confirm again with `accept_invite`. An inviter cannot supply consent on the requester's behalf. Unpaired callers need no flag. Neither the private consent ledger nor another couple's id is exposed. This flag records the caller's explicit assertion; the database cannot verify which UI produced it.

**Error format:** the exception message is exactly the code (`error.message === 'COUPLE_FULL'`). **Exception (BE-04, BE-26): `accept_invite`, `invite_preview`, `approve_join` and `decline_join`.** A raised error rolls the transaction back, which would also roll back the record of the failed attempt that the D02 limiter needs. So when one of them rejects a typed code with `INVALID_CODE`, `INVITE_EXPIRED` or `COUPLE_FULL`, it commits the attempt and answers **HTTP 400 with the body `{"code":"P0001","message":"INVALID_CODE","details":null,"hint":null}`** (PostgREST `response.status`). supabase-js turns that into `error` exactly as for a raise, so `error.message === 'INVALID_CODE'` holds and no client branch is needed; do not rely on `data` being set. `approve_join` / `decline_join` return `JOIN_REQUEST_EXPIRED` for an expired request the same way (the expiry and the failed attempt commit). `accept_invite` also returns `RATE_LIMITED` as a 400 body when the pending-request cap is reached or an expiry just reaches the failed-attempt limit, preserving any expiry accounting. Other errors (including the initial limiter check, `RATE_LIMITED`, `OWN_CODE`, `ALREADY_PAIRED`, `NOT_AUTHENTICATED`) are raised as before. Because these two RPCs return `json`, the generated type of `data` is `Json` (a couple-id string for `accept_invite`). The app maps codes to text in `src/lib/errors.ts`; an unknown code shows a generic error. Complete list: `NOT_AUTHENTICATED`, `NOT_PAIRED`, `ALREADY_PAIRED`, `INVALID_CODE`, `INVITE_EXPIRED`, `COUPLE_FULL`, `OWN_CODE`, `RATE_LIMITED`, `JOIN_REQUEST_EXPIRED`, `JOIN_REQUEST_FORBIDDEN`, `CONFIRM_ARCHIVE`, `LIBRARY_EXHAUSTED`, `PREMIUM_REQUIRED`, `SAVER_UNAVAILABLE`, `PARTNER_ALREADY_ANSWERED`, `NUDGE_LIMIT`, `QUESTION_UNAVAILABLE`, `INVALID_REACTION` (BE-40: `reactions.kind` is not exactly one emoji; raised by the table write, not an RPC), `INVALID_ONBOARDING_ANSWER` (BE-48: an `onboarding_answers` row of questionnaire version 2 with an unknown question id or choice key; raised by the table write), `ANSWER_TOO_LONG` (BE-41/D46: an `answers` body over the couple's current limit, 500 free / 2000 Premium; `details` = JSON string `{"max":n}`; raised by the table write), `INVALID_VOICE` (BE-42/D46: a new `voice_path` on an answer or message that is not an uploaded object in the writer's own `{couple_id}/{uid}/` folder of the `voice` bucket, or is already used by another row; raised by the table write). PREMIUM_REQUIRED (listed above) is also raised by the table write for a new voice answer or message in a free couple (BE-42).

The same list is the Postgres enum `error_code`, exported in the generated types as `Database['public']['Enums']['error_code']` (map it exhaustively); `supabase/tests/error-codes.test.mjs` fails if this line and the enum differ. Codes are raised with SQLSTATE `P0001` (HTTP 400). Every authenticated app RPC raises `NOT_AUTHENTICATED` when the JWT has no user. Every app RPC except `invite_preview` is granted to `authenticated` only, so an `anon` call fails before it runs with Postgres `permission denied` (`42501`, not a code): treat it as signed out. The RPCs in the table above are the whole callable app API (service-only Edge seams are documented in §3): the RLS helpers (`my_couple_id`, `is_cq_member`, `has_answered`, `both_answered`, `answer_cq`, `message_cq`, `is_couple_premium`) live in the unexposed `private` schema (BE-24).

**Service-only BE-18 RPC:** `apply_revenuecat_event(p_event_id text, p_occurred_at timestamptz, p_changes jsonb)` → `void`; each change is `{user_id, is_active, product_id, store, expires_at}`. Only `service_role` can execute it. It atomically dedupes event IDs, ignores equal/older per-user timestamps, updates all affected users and dispatches newly premium couples. The private helper/ledger have no API-role access; client entitlement writes are revoked. Invalid internal input raises fixed `INVALID_WEBHOOK` (SQLSTATE `22023`); this internal validation error is outside the client `error_code` enum. Deleted/unknown profiles are skipped. No user JWT subject is required for this service-only entry point.

### Finishing onboarding right after sign-in (D50, BE-48)

No `finish_onboarding` RPC: every step below is an existing, retry-safe call, so the app runs them in this order after sign-in and simply retries a failed step (the local copy stays until each write succeeds). Only for a new person who went through onboarding; a returning user (D40) and a joiner (D29) skip it.

1. **Sign-in.** The auth trigger already created `profiles` and `notification_prefs` (ritual 21:00, reminders on).
2. **`Purchases.logIn(uid)`**, then **`revenuecat-sync`** (§3) if the person bought on P3 (or always: it is cheap and rate-limited). Premium shows only after the server `entitlements` row says so (§6).
3. **Profile:** `from('profiles').update({ display_name, timezone })` (07 name; device IANA zone). Do this **before** step 4: the couple copies the profile timezone when it is created.
4. **Solo couple:** `create_couple(p_stage, p_goals, p_partner_name)` with 05, 06 and the partner name from 07. A retry while solo returns the same id and updates the settings. `ALREADY_PAIRED` means the account is already in a couple: stop here and drop the local T1 answer.
5. **Ritual time (N):** `from('notification_prefs').upsert({ user_id, ritual_time }, { onConflict: 'user_id' })` (`HH:MM`, 08:00 / 12:30 / 21:00 / other). Save it also after "Not now": leave `daily_reminder` as it is, since without a push token nothing is sent, and reminders start once the person allows notifications later (09/Settings register the token).
6. **Onboarding answers:** upsert the three version-2 rows (above).
7. **T1:** `get_daily_question()` (day 1 of the new couple is the `first_day` question, D12), then `from('answers').upsert({ couple_question_id, user_id, body }, { onConflict: 'couple_question_id,user_id' })`. **Omit `client_written_at`** for this answer: arrival time makes it count for the couple's first local day; an onboarding device time from an earlier day would save it with `counts_for_streak = false`. The answer is locked for the partner until they answer (reveal rule) and the joiner gets the same question.

Steps 5 and 6 don't depend on the couple and can run in parallel with 3–4. Tested in `supabase/tests/onboarding-v2.test.mjs`.

### Realtime (backend publishes, mobile subscribes)

Tables in `supabase_realtime`: `couple_questions`, `answers`, `thread_messages`, `reactions`, `couple_members` (BE-20), and `join_requests` (BE-26; requester/inviter only). RLS applies to events.

The app opens **one** channel, `couple:{couple_id}`:
- `postgres_changes` on `couple_questions` (filter `couple_id=eq.{couple_id}`) → invalidate today and that question.
- `answers`, `thread_messages`, `reactions` (RLS scopes them) → invalidate the affected question and thread.
- `couple_members` → the partner joined, during pairing; also the **end of the couple** (BE-38): `unpair` and account deletion both UPDATE the remaining member's own row (`left_at`), which RLS admits for the ended couple's 30-day window, so the remaining partner's channel receives it and refetches the couple (`ended_by`, `ended_reason`). `couples` itself is not published.
- **Presence/broadcast** event `typing` `{ user_id, couple_question_id }`, sent at most every 3 s while typing, expiring after 5 s (D15). No database writes.

Events are only signals; the app always refetches instead of trusting the payload.

## 6. Subscriptions (RevenueCat): mobile + backend

- **The app calls `Purchases.logIn(supabaseUserId)` after sign-in and `logOut` on sign-out.** The RevenueCat `app_user_id` **is** the Supabase user id.
- Entitlement `premium`. Products: `yearly_trial` (7-day trial), `monthly`.
- Offerings (D52, BE-47): `default` (paywall 16/17, 34: yearly with the 7-day trial, monthly without) and `day3` (coupon 15: 25% first-year introductory price on yearly). `intro` and `winback` are retired. The server decides whether the `day3` gift is shown (`get_offer`/`open_offer`); RevenueCat's per-device intro eligibility is a second gate on the phone. The server never grants premium from an offer.
- Prices always come from the offering; nothing is hard-coded.
- BE-18 handles INITIAL_PURCHASE, RENEWAL, PRODUCT_CHANGE, UNCANCELLATION, NON_RENEWING_PURCHASE, CANCELLATION, BILLING_ISSUE, EXPIRATION and TRANSFER. It refreshes the canonical RevenueCat v1 subscriber `premium` entitlement using `REVENUECAT_REST_API_KEY`, then writes `entitlements`: `is_active`, `product_id`, lower-case `store`, `expires_at`, `updated_at` (event timestamp). A cancellation/billing issue retains premium through the current period/grace; PRODUCT_CHANGE does not grant a deferred product early; an expiration cannot revoke another still-active premium product. Missing premium becomes inactive; lifetime expiry is null. `expires_at` stores the later of canonical paid expiry and grace expiry (entitlement or matching subscription), so database checks retain access during grace and revoke at its exact boundary; cleared grace uses the new paid expiry. Malformed grace gets a retryable 500 without writes. Fixtures: `qa/fixtures/revenuecat-events.json`.
- TRANSFER refreshes UUID aliases on both sides, preserving any remaining source entitlement; anonymous IDs are ignored. **BE-48 (D50, purchase on P3 before sign-in):** ordinary events (and the legacy `SUBSCRIBER_ALIAS`) refresh every Supabase UUID named in `app_user_id`, `original_app_user_id` or `aliases`, so an event for `$RCAnonymousID:…` delivered after `logIn(uid)` lands on `uid`. Each UUID gets only its own canonical RevenueCat state (a second UUID in aliases never inherits the buyer's premium); at most 10 UUIDs, ids used exactly as sent (case-sensitive). **BE-48c (#167):** only the canonical lower-case UUID spelling is a Supabase uid; any other spelling (upper/mixed case) is a foreign id like an anonymous one: never looked up, never written (in ordinary events and in TRANSFER lists), and `apply_revenuecat_event` rejects non-canonical `user_id` text with `INVALID_WEBHOOK`. `app_user_id` must be a UUID (any case) or an anonymous id, `aliases` an array of ≤50 strings, otherwise `400`. Events naming **only** anonymous ids (bought, not signed in yet) get 200 plus a fixed log event, no lookup and no write: `revenuecat-sync` (§3) after `logIn` applies the purchase, since RevenueCat sends no webhook for the alias itself. Logs carry only event names and a count, never ids. Unsupported event types/unrelated entitlements get 200 without writes. Missing REST secret, failed/malformed lookup or database failure gets fixed `500 INTERNAL_ERROR` for retry. Auth is checked before body/admin access; bodies are bounded to 64 KiB. Payloads, receipts, REST responses and credentials are never logged/stored.
- A private event ledger dedupes `event.id`; equal/older per-user timestamps are ignored. **BE-48b:** the webhook stamps its write with `max(event time, lookup time)` because it always writes a fresh canonical snapshot, so a refund/cancel webhook delivered after a `revenuecat-sync` (stamped with its own lookup time) is not dropped as stale. **BE-48c:** an event time more than 5 min after the lookup is clamped to lookup time + 5 min, so clock skew or a bad timestamp cannot freeze the row. All transfer changes and dispatch commit together; failure rolls back the claim. When an active couple becomes premium, BE-08 sends `partner_premium` to the other member using the copy template and `bonded://packs`. Renewals/already-premium couples and transfers within a premium couple do not produce another activation. Recipient quiet hours, four/day and one premium push/day caps apply. Missing Vault/notify setup can drop the push without losing the entitlement; an uncertain push is not replayed by resending the purchase event. Mobile refetches premium on purchase/restore/foreground/push; Realtime publication is unchanged.
- **BE-48 trial state:** the canonical snapshot also carries the subscription's `period_type`, `purchase_date` and will-renew (no `unsubscribe_detected_at`/`billing_issues_detected_at`). The database keeps them in a private table (not on `entitlements`, so a partner never learns that a trial was cancelled), ordered like the entitlement (stale events ignored) and removed with the account; they drive only the `trial_ending` push (§3). The app reads trial details from the RevenueCat SDK if it needs them.
- **Order after sign-in (D50):** `Purchases.logIn(uid)` → `revenuecat-sync` → refetch `entitlements`. A purchase on P3 is never shown as Premium from the SDK alone.
- App premium comes from the server `entitlements` rows for the signed-in user and their **current** partner: either row grants premium only when `is_active = true` and `expires_at` is null or later than the check time. Readable former-partner rows do not grant premium. RevenueCat SDK customer info only triggers an entitlement refetch; purchase/restore waits for server confirmation before showing premium success. The app evaluates expiry at fetch time and refetches on foreground/reconnect; the database enforces the exact expiry boundary using its clock. The server checks stored entitlements: `private.is_couple_premium()` for packs; streak saver additionally requires current membership and checks expiry against the server clock. Private helpers are not callable from the app.

## 8. Shared conventions
- IDs are UUIDs. Timestamps are `timestamptz` in UTC. Dates (`assigned_for`, `local_date`) are the couple's local date; the couple's timezone is the inviter's.
- Text limits: answers 1–500 characters for free couples, 1–2000 while the couple is Premium at write time (D46, BE-41; after a lapse long answers stay readable, edits only down to ≤ 500; error `ANSWER_TOO_LONG` with `details.max`), thread messages 1–2000 for everyone. The DB enforces them; the app mirrors them.
- Test ids: `testID="<screenId>-<element>"` (for example `20-hold-button`), used by Maestro.

## 10. Email authentication links and codes (owner: lead, D35)
- The app requests email authentication with `signInWithOtp` and the redirect `bonded://auth/callback`.
- Email-link callbacks accept PKCE authorization codes only, exchanged with the initiating app's stored verifier. Implicit bearer-token callbacks and mixed code/token callbacks are rejected; older implicit links require a fresh email or manual OTP entry.
- The Supabase `magic_link` email template includes both `{{ .ConfirmationURL }}` and `{{ .Token }}` so the user can either tap the sign-in link or enter the six-digit code with `verifyOtp({ email, token, type: 'email' })`. The `confirmation` template includes both values as well, for projects that require email confirmation.
- The Auth redirect allow-list explicitly includes `bonded://auth/callback`. The app handles the callback and establishes the session before leaving the signed-out state; an invalid or expired link returns to sign-in without preventing manual code entry.
