# Release-candidate checklist

**Owner:** release validator. Run every row on **iOS and Android** unless the row says otherwise. Screen-level rows (one per P0/P1 screen) are in `screen-requirements.csv`. This file holds the cross-cutting checks. Method and report format: the `bonded-release-check` skill.

A P0 row that fails, or that has no evidence, makes the build **NO-GO**.

**Where Android rows run:** on the local emulator (AVD `Medium_Phone_API_37.0`, Android 17, Google Play image; `emulator -avd Medium_Phone_API_37.0`, wait for `adb shell getprop sys.boot_completed` = `1`, then `npm run android`). Only these stay blocked until a real device or an EAS build: push delivery (FUN-09, the push half of FUN-24, `offer_ending`, `trial_ending`), Apple and Google sign-in (IOS-01), haptics (UI-06), store purchases and restore (BIZ-02, BIZ-08, BIZ-10, BIZ-11, BIZ-18, the buy step of BIZ-13 and BIZ-16, the iOS cancel offer of BIZ-25, the `cancel30` trial check BIZ-30, the `cancel_offer` push of BIZ-28), store console checks (BIZ-26), the production-build key check (HYG-09, needs the EAS production build), and store checks (AND-03, AND-06, STORE-*). Everything else on Android is run on the emulator, never marked `blocked` for lack of a device.

**RevenueCat Test Store (D60, PO 2026-11-13):** dev and preview builds carry the Test Store `test_…` key (Test Store products `yearly_v2`, `monthly_v2`, `yearly_day3_v2`, `yearly_exit30_v2`). A Test Store run is valid evidence for the app's offering, price, % and flow rows on a **dev/preview build only**; it never counts as evidence for a release candidate's store purchase rows (those need App Store sandbox / Play license testers on the production build), and the iOS `cancel30` promotional offer cannot run in the Test Store (BIZ-25, BIZ-30 stay `blocked` until the store phase).
